## 2.1 问题：评测集混入了训练格

### 2.1.1 现象

`stratified_subset(pool, 40, seed=20261107)` 这个函数在开发过程中被改过（修了一个分层 bug）。**今天调用它得到的 40 格，与主 checkpoint 实际训练的 40 格不同。**

对比（`scripts/verify_eval_leakage.py`）：

| Checkpoint | 记录的 40 格 | 与今天的设计重叠 | 今天的留出集中有 **32 格是它的训练格** |
|---|---|---:|---:|
| `two_32000`（主结果）| $s11\_m05, s15\_m05, s19\_m05$ 等 | **6 / 40** | **32 / 144（22%）** |
| `two_32000_s89` | 同上 | 6 / 40 | **32 / 144** |
| `train/lhs40` | $s01\_m05, s03\_m05, ...$ | 9 / 40 | **28 / 144（19%）** |
| `capacity_matched w112` | 与今天一致 | **40 / 40** | **0** ✅ |
| `extrapolation mf_s88` | 45 格 | 7 / 45 | **34 / 144（24%）** |

### 2.1.2 受影响的脚本

任何在运行时**重算**设计而非从 checkpoint 读取的脚本：

- `scripts/four_way_compare.py` ← 四项对照
- `scripts/alpha_sweep.py` ← α 扫描
- `scripts/capacity_matched.py` ← 容量匹配（**评测集错，但训练集对**）
- `scripts/interp_baseline.py`
- `scripts/dp_two_param.py`（若重跑）

### 2.1.3 未受影响

- 主结果（`two_32000` / `dp_two_param`）：这些是**当初**用正确设计训练并评测的，`detail.csv` 里记录的就是正确留出格
- `rollout/`、`physics/`：只用 6 个指定格，不涉及 144 格划分
- `displacement/`、`continuity/`：只用物理云，与模型无关

### 2.1.4 已修复：影响远小于预期

`scripts/repair_eval_sets.py` 从 checkpoint 读取权威训练格，重建留出集（**143 格**，不是 144），重跑全部对照：

| 配置 | 污染版（144 格）| **修复后（143 格）** | 差异 |
|---|---:|---:|---:|
| MF 一步 | 0.12219 | **0.12277** | +0.0006 |
| MF + DP，$\alpha{=}1$ | 0.10376 | **0.10429** | +0.0005 |
| MF + DP，$\alpha{=}2$ | 0.09515 | **0.09566** | +0.0005 |
| MF 两步 | 0.12332 | **0.12418** | +0.0009 |

**差异只有 0.5%。** 污染的 32 格恰好都是**容易的格**（模型记性好），所以剔除后数值微微变差但结论不变。

**交叉验证**：修复后的 $\alpha{=}1$ 值 **0.10429** 与主结果 `dp_two_param/s88` 的 MF+DP 值 **0.10429 完全一致**，证明修复是正确的（路径不同，结果相同）。

> **结论**：这是一个**真实的方法论缺陷**（任何重算设计的脚本都不可信），但**幸运地不影响任何定性结论**。所有引用四项对照的地方应改用修复后的数字。

### 2.1.5 修复方案（已成文）

**唯一正确做法：从 checkpoint 读训练格，绝不重算。**

```python
payload = torch.load(checkpoint, weights_only=False)
train_cells = set(payload["cells"])          # 权威来源
held = [c for c in pool
        if c.key not in train_cells
        and c.key not in {b.key for b in G.baseline_slice()}]
```

已实现：`scripts/verify_eval_leakage.py`（核查）、`scripts/repair_eval_sets.py`（修复+重算）。

## 2.3 两篇论文带来的额外要求

### 2.3.1 MeanFlow 论文（2505.13447）

读完后的关键点，影响我们如何定位：

| MeanFlow 的做法 | 我们的做法 | 是否需要说明 |
|---|---|---|
| 学**平均速度** $u(z,r,t)=\frac{1}{t-r}\int_r^t v$ | **相同**（上游已实现）| 不是我们的贡献 |
| 恒等式 $u=v-(t-r)\frac{du}{dt}$，JVP 求 | **相同** | 不是我们的贡献 |
| 1-NFE 一步生成 | **相同** | 不是我们的贡献 |
| **无预训练、无蒸馏** | **相同** | ✅ |
| 用 CFG 融入目标场 | 未用 | 无关 |
| 图像生成（ImageNet FID 3.43）| PDE 粒子云 | 应用不同 |

**Harry 的潜台词**：MeanFlow 已经解决了"一步生成"这个数学问题。**你的贡献不能是"我们也能一步"**，必须是"多物理参数化 + 第二步修正"这一层。

### 2.3.2 OT-CFM 论文（2302.00482）

| OT-CFM 的做法 | 我们的做法 | 区别 |
|---|---|---|
| minibatch OT 改进**耦合**（$x_0,x_1$ 配对）| minibatch OT 构造**修正目标** | **用途不同** |
| 目标是**变直**轨迹、减少 NFE | 目标是**分布匹配** | **目标不同** |
| 用 Sinkhorn（熵正则）/ 精确 OT | **精确 OT**（network simplex）| 我们更贵但无偏 |
| 近似动态 OT（NPE 指标）| 不涉及 | 无关 |
| 论文明说：minibatch OT 有误差但"低损" | 我们的 batch 2000 vs 全量 10 万 | **同样的近似** |

**Harry 的关键提醒**："avoiding global OT is different from eliminating all OT computation"。

- 我们**训练时**仍需 minibatch OT（约 7% 训练时间）
- 我们**部署时**零 OT
- 这一点必须明说，不能宣称"我们不需要 OT"

### 2.3.3 两篇都提的一个点：容量匹配

- MeanFlow 论文里所有对比都控制参数量
- OT-CFM 论文里对比 I-CFM / OT-CFM 用**同一网络**

**所以 Harry 要求 (c) 容量匹配是这两篇的标准做法，不是刁难。**

# 第五部分：给 Harry 的定位陈述（草稿）

> **我们的贡献不是"一步生成"**——MeanFlow 已经解决了这个问题。
>
> **我们的贡献是**：把一步生成扩展到**双物理参数**，并回答三个具体问题：
>
> 1. **参数依赖性有多强？** 一个可检验的经验定律：$W_2\approx 0.90|\Delta(\sigma T)|+1.98|\Delta\sqrt{2\mu T}|$，两个常数在 20 倍参数范围内稳定（$c_S$ 变异系数 15%）。这给出了"什么参数间距可以被分辨"的先验判据。
>
> 2. **第二步修正值不值？** 在**参数几乎相同**（差 0.17%）、**推理成本相同**（2 次前向）的条件下：
>    - 加修正器：$0.1222\to0.1038$（$+15\%$）
>    - 加一步 MeanFlow：$0.1222\to0.1233$（**$+0.9\%$，无用**）
>    - 加宽到同参数量：$0.1222\to0.1160$（$+5\%$，不如修正器）
>
> 3. **修正的边界在哪？** 修正器**只修训练分布内的误差**：内插 $+14.7\%$，$\sigma$ 外推 $+1.3\%$，$\mu$ 外推 $+2.4\%$。**这是负面结果**，说明它不是修复可识别的系统性偏差，而是补偿训练分布。
>
> **明确的限制**：生成器不能迭代（$k\ge2$ 即发散，$k=8$ 时误差达 $4\times10^4$ 倍底噪）。长时程需要重训模型，不是重复应用。
